## Go's distribution surfaces (inventoried before porting)

- **Release set (`make artifacts`):**
  - `host-agent-linux-x64`: cgo, dynamically linked, needs glibc 2.34.
  - `host-agent-linux-arm64`: static.
  - The Windows `.exe`, gzipped and renamed `host-agent-windows-x64.gz`.
  - Three providers (k3s, cloudflare, tailscale).
  - Both Linux binaries are compressed with `gzip -9 -kf`.
  - `SHA256SUMS` lists, in order: the plain x64 binary, the x64 archive, the
    arm64 archive, the Windows archive, then the providers.
  - `VERSION` defaults to `0.2.3`.
- **Deploy files:**
  - `deploy/opute-host-agent.service`, a user unit. It runs
    `%h/.local/share/opute/opute-host-agent` with
    `EnvironmentFile=%h/.config/opute/host-agent.env`.
  - `deploy/opute-bootstrap-mcp.service`, a system unit: `User=opute`,
    listening on `0.0.0.0:3014`, with no identity.
  - `deploy/opute-host-agent-sudoers`.
- **No installer script in the Go tree.** The production install script is
  generated by the Platform, which owns it. The clean-machine journey
  (`tools/parity/t2guest/distjourney.py`) therefore does only what the
  published files require:
  - download from the release base and verify against `SHA256SUMS`;
  - unpack into the unit's `ExecStart` path;
  - write the env file and install the units and the sudoers file;
  - enable and start with systemd.
- **npm launcher (`npm/local-host-agent`):**
  - Downloads `<base>/v<version>/host-agent-<target>.gz` and verifies it
    against `SHA256SUMS`.
  - Writes a `.verified.json` marker and caches under a `<version>.lock`
    directory lock.
  - Spawns the binary and proves ownership through `localInstanceId`.
  - Go's `local-npm-readonly-canary` packs the launcher and runs
    `published-readonly-canary.test.js` with `OPUTE_HOST_AGENT_BINARY`. The
    round runs exactly that.
- **Site (`check-site`):** capture test, catalog capture, `generate-docs.ts`,
  then eight Python checks.

## Rust changes M10 needed

Both were found by the M10 comparisons; each is one commit.

- **`--version` reports the release `VERSION`.**
  - `OPUTE_HOST_AGENT_VERSION` at build time, as Go's `-ldflags -X`.
  - Without it, the crate version is used, which is Go's default `0.2.3`.
- **The go-sdk session lines in the log.**
  - Go logs, per HTTP request:
    - `server connecting`;
    - `server session connected`;
    - for new-protocol requests, `client log level set` after the session
      checks;
    - `method removed in the new protocol` for removed methods;
    - `server session disconnected` at the end.
  - Notifications never log the level line.
  - An 18-case matrix (`dist.LOG_CASES`) now gives identical lines.

## Building the release set

- `make release-toolchain` pins zig 0.15.2 (by sha256) and cargo-zigbuild
  0.23.4.
- `make artifacts` builds:
  - `x86_64-unknown-linux-gnu.2.34`: glibc floor 2.34, the same as Go's.
    A plain `cargo build` needs `GLIBC_2.39` and would not start on
    Debian 12 or Ubuntu 22.04.
  - `aarch64-unknown-linux-musl`: static, as Go's is.
- The providers are Go's, built with Go's own targets from an export of the
  pinned tree (D2: M9 is optional).
- Go records the build directory in its binaries, so both the Go release set
  and the providers are exported to a fixed path. With that, every binary
  reproduces byte for byte on a cold rebuild.
- The `.gz` archives differ between builds only by the input mtime that
  `gzip -9 -kf` records. That is Go's own recipe, kept unchanged.
- Each release set is therefore pinned as built, by its `SHA256SUMS`, and the
  round rebuilds both sets to prove the binaries reproduce.

## Findings

1. **Go's release policy refuses the Rust catalog for the stable package.**
   - `site/scripts/capture-catalog.mjs` stops with "a stable package version
     cannot publish a different catalog revision".
   - Rust's catalog differs by the approved D19/D21–D24 naming, so it has its
     own revision. Publishing a Rust build as `@opute/host-agent@0.2.3` is
     impossible without a new package version.
   - That is a release decision for 5.2 and the cutover, not M10. The round
     records the refusal as expected (`rustStableRefused`).
2. **The published bootstrap unit carries no identity.**
   - Started as published, it fails on both Go and Rust: "OPUTE_REMOTE_AGENT_ID
     is required; the host agent must be onboarded with one canonical id".
     The unit then auto-restarts.
   - The journey checks that refusal, then starts the unit with an identity
     drop-in (`Environment=OPUTE_REMOTE_AGENT_ID=…`, `MCP_AUTH_TOKEN=…`), as
     an operator would.
3. **systemd's accounting line depends on how much the unit used.**
   - systemd logs `<unit>: Consumed … CPU time, … memory peak` only when a
     unit's usage crosses its reporting thresholds.
   - In the dry runs Go's bootstrap unit crossed them and Rust's did not, so
     the line is masked on both sides (`systemd-accounting`) wherever it
     appears. It measures consumption, not behavior. In round 1 neither unit
     logged it, so the mask did not apply.
4. **`npm exec` races itself.**
   - Two cold `npm exec --package=<tgz>` runs that share an npm cache can
     both install the tarball at once. One then fails with
     `opute-host-agent: not found`.
   - This is npm's own concurrency, not the launcher's. The concurrent-lock
     test installs the package once (`help`, which downloads nothing) before
     the two launchers race on the launcher's download lock.
5. **Finding F-4 needs more samples.** A recapture with 16 runs of
   `recipe validate` saw only one variant of the two-variant message.
   Sampling is now 64 runs, and F-4 is kept.
6. **Go's Windows build fails offline.** The pinned offline module cache lacks
   `modernc.org/libc`'s Windows files. The Windows artifact is an owned gap
   on both sides.
7. **bun is not in the pinned toolchain.**
   - `generate-docs.ts` runs on the pinned node 22.14 with
     `--experimental-strip-types`.
   - The substitution is proven faithful: Go's committed site reproduces byte
     for byte from Go's binary, and all eight checks pass.
